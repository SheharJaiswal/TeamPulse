# Identity Service – Approved Baseline Specification

## Purpose

Authenticate TeamPulse users and provide authoritative employee identity, organization, team and role information.

## Scope

Employee persistence; HR-controlled provisioning baseline; password-based login; short-lived JWT issuance; authenticated /me endpoint; Development-only bootstrap registration; HR-authorized employee lifecycle status commands.

## Business rules

- Employee IDs are generated by Identity Service.
- Every employee must belong to an organization. Team membership is optional and can be assigned later; personal employee capabilities do not require a team.
- Email is normalized for uniqueness.
- Identity owns canonical TeamPulse employee, organization, team and role records. HRIS is the authoritative upstream employment/membership source when integrated; authorized HR administrators maintain records until then.
- Production onboarding is HR-controlled provisioning/invitation only. Public self-registration is disabled outside Development.
- Passwords use ASP.NET Core password hashing.
- An employee whose IsActive flag is false cannot authenticate. The login response is the same generic 401 used for other invalid credentials. Identity verifies the submitted password for an existing account, but does not generate/upgrade a password hash, persist changes or issue a token for an inactive employee.
- When password verification reports SuccessRehashNeeded for an active employee, Identity upgrades and persists the password hash before issuing an access token. A failed persistence operation must not result in token issuance.
- JWT contains sub, email, name, organization_id and role. The `team_id` claim is included only when the employee has a team assignment; an unassigned employee has no `team_id` claim.
- Receiving services validate issuer, audience, signature and expiry.
- Authorization is enforced by every receiving service.
- JWT signing keys are supplied through environment/secret-store configuration and are never committed in appsettings or source control.
- Signing keys must contain at least 32 UTF-8 bytes; missing, blank or weak values prevent startup.
- The bootstrap registration endpoint is enabled only in the Development host environment; it returns 404 in all other environments.

## HR-authorized lifecycle rules

- HR controls employee activation and deactivation. The bootstrapped `HrAdmin` role is the only interactive role authorized for the lifecycle endpoints in this increment.
- The actor is the validated JWT `sub`; a request cannot supply or override the actor identity.
- Organization Admins cannot directly edit employee profile fields or activate/deactivate employees. They may request HR changes; no request-intake workflow is implemented.
- HR owns canonical employee fields (email, display name, organization ID, optional team ID and role). This increment does not expose profile/role mutation endpoints. The role catalogue and elevated-role assignment policy remain undefined.
- Deactivation blocks new Identity login after commit. Reactivation requires an explicit HR command and does not restore prior sessions.
- Every real transition records actor/source, target employee ID, old/new status, UTC time, reason code, optional note and correlation ID.
- Every real transition increments a per-employee lifecycle version and atomically persists the employee update, immutable audit row and schema-v1 outbox record.
- Same-state commands are no-ops. Idempotency keys prevent duplicate transitions; conflicting reuse is rejected.
- `EmployeeDeactivated` and `EmployeeReactivated` events use the shared envelope and are delivered at least once by the future dispatcher. The outbox record alone is not proof of delivery.
- Receiving services maintain local, version-aware employee status projections; no service reads Identity's database. Until all consumers are deployed, stateless JWTs may remain usable until expiry.
- Password hashes, credentials, tokens and wellness/activity details are never included in lifecycle events.

## Acceptance criteria

- IA-01: Reject missing required fields and passwords shorter than 12 characters.
- IA-02: Reject duplicate normalized email.
- IA-03: Persist only one-way password hash.
- IA-04: Generic login failure for unknown email and wrong password.
- IA-05: Signed JWT with configured issuer, audience and expiry.
- IA-06: Anonymous access to /me is denied.
- IA-07: /me returns claims from validated token.
- IA-08: Missing, blank, whitespace-only or fewer than 32 UTF-8 bytes signing key prevents startup with an actionable configuration error.
- IA-09: Inactive employees receive the generic login 401; submitted password verification is performed, but hash generation/rehashing, persistence writes and token issuance are skipped.
- IA-10: POST /api/identity/register is available only when the API host environment is Development; in all other environments it returns HTTP 404 and performs no persistence.
- IA-11: When the password hasher returns SuccessRehashNeeded for valid active credentials, the service stores a replacement hash before issuing a token; Success does not rewrite the hash, Failed remains a generic 401, and persistence failure prevents token issuance.
- ILC-01 through ILC-12: See [HR lifecycle change acceptance criteria](../changes/identity-hr-employee-lifecycle/spec.md).

## Lifecycle boundary and deferred work

Employee invitations/provisioning, HRIS integration, profile/role mutation, Organization Admin request intake, outbox transport dispatch and downstream status projection implementations are separate increments. The current `IsActive` login guard is not global token revocation. Retention defaults require jurisdiction-specific privacy/legal review before production.
