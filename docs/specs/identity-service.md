# Identity Service – Approved Baseline Specification

## Purpose
Authenticate TeamPulse users and provide authoritative employee identity, organization, team and role information.

## Scope
Employee persistence; HR-controlled provisioning baseline; password-based login; short-lived JWT issuance; authenticated /me endpoint; Development-only bootstrap registration.

## Business rules
- Employee IDs are generated by Identity Service.
- Email is normalized for uniqueness.
- Identity owns canonical TeamPulse employee, organization, team and role records. HRIS is the authoritative upstream employment/membership source when integrated; authorized HR administrators maintain records until then.
- Production onboarding is HR-controlled provisioning/invitation only. Public self-registration is disabled outside Development.
- Passwords use ASP.NET Core password hashing.
- An employee whose IsActive flag is false cannot authenticate. The login response is the same generic 401 used for other invalid credentials. Password verification/rehashing and token issuance are skipped for inactive employees.
- When password verification reports SuccessRehashNeeded for an active employee, Identity upgrades and persists the password hash before issuing an access token. A failed persistence operation must not result in token issuance.
- JWT contains sub, email, name, organization_id, team_id and role.
- Receiving services validate issuer, audience, signature and expiry.
- Authorization is enforced by every receiving service.
- JWT signing keys are supplied through environment/secret-store configuration and are never committed in appsettings or source control.
- Signing keys must contain at least 32 UTF-8 bytes; missing, blank or weak values prevent startup.
- The bootstrap registration endpoint is enabled only in the Development host environment; it returns 404 in all other environments.

## Acceptance criteria
- IA-01: Reject missing required fields and passwords shorter than 12 characters.
- IA-02: Reject duplicate normalized email.
- IA-03: Persist only one-way password hash.
- IA-04: Generic login failure for unknown email and wrong password.
- IA-05: Signed JWT with configured issuer, audience and expiry.
- IA-06: Anonymous access to /me is denied.
- IA-07: /me returns claims from validated token.
- IA-08: Missing, blank, whitespace-only or fewer than 32 UTF-8 bytes signing key prevents startup with an actionable configuration error.
- IA-09: Inactive employees receive the generic login 401; password hashing/rehashing, persistence writes and token issuance are skipped.
- IA-10: POST /api/identity/register is available only when the API host environment is Development; in all other environments it returns HTTP 404 and performs no persistence.
- IA-11: When the password hasher returns SuccessRehashNeeded for valid active credentials, the service stores a replacement hash before issuing a token; Success does not rewrite the hash, Failed remains a generic 401, and persistence failure prevents token issuance.

## Lifecycle boundary
HR activation/deactivation commands, HRIS integration, lifecycle audit records, transactional outbox publication and downstream status projections are separate implementation increments defined by ADR-0002. The login guard enforces existing status only and does not implement those workflows.
